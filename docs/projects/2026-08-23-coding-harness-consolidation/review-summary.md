# Coding-harness consolidation — R1 review summary

## Review process

Four independent attack passes were completed before consolidation:

1. Architect — state ownership and dependency direction.
2. Maintainer/Ops — total lifecycle cost.
3. Skeptic/Product — user-visible value and over-design risk.
4. Evaluator/Verifier — falsifiability and deterministic local tests.

All four returned `FIX-THEN-SHIP`. None recommended an active daemon, bridge architecture, or Pi/DSH primary-runtime migration.

## Converged decision

The plan's first product must be a **Host Conformance Harness**, not another coding harness.

It will test and report whether canonical Autopilot behavior is honestly delivered through current host packages and worker surfaces. The result can select:

- **Option 0:** keep generated distribution and current core;
- **Option A:** extract only a named manually duplicated semantic into the canonical root core.

Options B/C are removed from active execution. They survive only as evidence-gated re-entry paths.

## Finding union and dispositions

| ID | Severity | Finding | Required disposition |
|---|---|---|---|
| R1-F1 | Critical | The original plan can finish as prose because W1–W3 have no executable target contract. | Define `autopilot.host-conformance.v1`, exact CLI commands, fixtures, and fail/pass oracles. |
| R1-F2 | Critical | P0/P1 create manual inventories that duplicate `sync-manifest.json` and generator truth. | Generate the inventory from repository/generator data; hand-written exceptions only. |
| R1-F3 | Critical | No user-visible deliverable exists when Option 0 wins. | Ship a usable conformance report/self-check even when architecture stays unchanged. |
| R1-F4 | Major | Host front doors and leaf worker integrations are conflated. | Freeze a capability matrix; unsupported is a valid result; Pi remains a worker surface. |
| R1-F5 | Major | W2 recovery lacks precise effect boundaries and call-count oracles. | Add four deterministic termination points and prove settled effects are not repeated. |
| R1-F6 | Major | No lifecycle ceiling prevents a “small” spike from adding a process/protocol/store. | Initial implementation budget: zero new process, protocol, state store, runtime dependency, or production package. |
| R1-F7 | Major | Supervisor/standalone runtime phases have no current product trigger. | Remove them from active phases; require two real incidents for service re-entry and a named unsatisfied capability for substrate re-entry. |
| R1-F8 | Major | Equal parity across every host would cause emulation or lowest-common-denominator behavior. | Report `supported`, `degraded`, `unsupported_by_design`; preserve native strengths. |
| R1-F9 | Minor | Review loop permits too many repairs and new-topic churn. | Exactly one consolidation repair plus one closure review; R2 cannot open unrelated findings. |
| R1-F10 | Minor | Repository-byte reduction is mistaken for maintainability. | Measure manual edit owners and semantic forks, not generated bytes alone. |

## Initial lifecycle budget

```text
new long-lived processes: 0
new protocols/sockets: 0
new state stores: 0
new runtime dependencies: 0
new production packages: 0
```

## Required deterministic fixtures

- F1 projection parity plus planted drift.
- F2 four-boundary Mission resume matrix with durable call counters and Git SHA oracle.
- F3 invalid reviewer output remains fail-closed through root and Codex packaged CLI.
- F4 fake Pi RPC directive/abort capability with no live model; optional live smoke remains separate.

## Review-loop cap

- R1: complete.
- Consolidation repair: one revision of the plan.
- R2: one closure verifier; it may only verify R1 dispositions or report regressions introduced by the repair.
- Any R2 failure ends at `BLOCKED/BOARD`; there is no third review generation.
