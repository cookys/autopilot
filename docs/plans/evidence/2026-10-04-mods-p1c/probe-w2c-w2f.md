 - Keys (jsonl rows): kind(stage|heartbeat|journal|worker_event), run_id, stage, state(leased|heartbeat|committed...), generation, nonce, pid, start_time, heartbeat_ts (epoch s), ts (ISO), reason. Latest row per run_id+stage (watch-foreman.js:243-253 keeps latest stage lease, folds heartbeat_ts in). Age = now - max(heartbeat_ts, ts). Rows are rotation-aware (src/campaign/cli.js:160 mirrors run-ledger rotation, RUN_LEDGER_MAX_BYTES 262144 default).
 - Binding to root_run_id: ledger rows carry run_id (= foreman run-id that depth-0 also exports as AUTOPILOT_ROOT_RUN_ID, level-front-door.md:262-266); leaf manifests carry root_run_id and watch-foreman.js:326-331 filters manifests by --root (manifests lacking root_run_id pass through). --root does NOT filter ledger rows (ledger chosen by --ledger path). So bind = job root_run_id -> ledger path (needs to be stored by depth-0) + filter rows run_id==root.
 - Classification W2c: NEEDS GUIDANCE (depth-0 must pre-assign/record the ledger path and the foreman must heartbeat via prose). A mechanism-only fallback exists for the LEAF layer (manifests + dispatch-detach 20s heartbeats keyed by root_run_id), which can show "last leaf activity age" but not "foreman stage". Mechanism-only for foreman stage = not possible without a code path that writes it (nothing does today for CC-native foremen).

(3) Window size: not in transcript. Transcript message.model is "claude-opus-5-5" with no [1m] suffix (same for 200K and 1M); hooks/context-budget.js:36-38 states this. Window arrives only from the status line: scripts/statusline-live-tee.js:44-48 reads payload.context_window.context_window_size (live file shows 1000000; model.id there also bare). A hook cannot know it from its own payload; it reads the live file (context-budget.js:143-146) or falls back to inference (inferWindowTokens: >200K observed proves 1M; <=200K ambiguous -> `windowUnknown`, context-budget.js:234-237) or from a configured value. Without the status line live file the % denominator is unknown (cannot discriminate 200K vs 1M until usage >200K).

(4) Cost / event: hooks/hooks.json:141-143 already runs hooks/context-budget.js on PostToolUse (default-on since v2.35.15) using readContextUsage(tpath) from hooks/context-budget-lib.js:185 (backward tail scan, window grows x4 to a cap). Stop is also available (payload has transcript_path) but fires once per turn, so PostToolUse is the finer-grained tick; Stop adds an end-of-turn exact value.

Verdict: FEASIBLE for tokens (exact), CONDITIONAL for percent. Already implemented in context-budget.js for tokens. Writer design if a % file is wanted without the status line: in the existing PostToolUse (and Stop) hook, readContextUsage(payload.transcript_path) -> {tokens, timestamp}; window = live-file context_window_size if present, else remembered per-session window (st.window), else inferWindowTokens(observedMax) (never below 200K, ratchet to 1M when tokens>200K), else configured default for the model id; write atomically (tmp+rename, mode 0600) a schema_version:1 record to resolveLiveDir().base/context/<sid>.json-like sidecar (separate file, e.g. <sid>.derived.json with `window_source: live|inferred|unknown`, used_percentage only when window_source != unknown) so it never overwrites the status-line live record. Honest limit: under 200K on a host with no status-line feed the percent is unknown, not 0.
