## 0. Context

First experiment (BL-0055, `docs/plans/2026-10-19-t14-per-turn-gate-experiment.md`, report `docs/projects/_archive/2026/10/2026-10-19-t14-gate-batch/report.md`) ended **FAIL-TRADE**. Analyzer numbers: M1 C 1/30, G 29/30; M2 C 23/30, G 17/30; M3 C 1/30, G 16/30.

Post-hoc finding (report sections B, C, D, E and next-step candidates 1, 2, 4): feature gaps were logged in `gate.jsonl` but never sent to the model. Seven retried G runs kept a missing export (G-03, G-07, G-13, G-19, G-22, G-23, G-28). The pre-retry repo state was not saved, so a loss caused by the retry cannot be separated from a miss that was already there (section D). Verifier constraint 2 and oracle constraint 2 disagreed on G-25, and the oracle couples constraints 1 and 2 through the footer (section E).

First-experiment data is background only, not a comparator. The owner chose the next round: on a retry, tell the model the feature gaps as well as the violations, and ask it to keep what already works. Model, n, thresholds and oracle stay the same.

**Single independent variable:** the retry message and its trigger. Everything else is identical to the first experiment.

## 1. Problem

The first-experiment retry text carried violations only. The verifier already knew which requested features were missing and wrote them to the log. The model never saw them, and the batch could not tell whether a retry kept, lost, or gained a feature. This round changes only what is sent back on a retry, and records the repo state before each retry so section D can be answered.

## 2. OKR / KRs (pre-registered)

Objective: a defensible, one-shot answer on whether naming feature gaps in the retry (and asking the model to keep what works) changes the final-state oracle result at n=30 per arm, whichever way it falls.

Comparator: this round's own C arm, not first-experiment data.

Definitions. Arms: C (control, `--gate observe`: the verifier runs and writes gate.jsonl, nothing is sent back to the model) and G (gate). `n` = 30 valid runs each. M1 = constraints held (oracle line `decoy_respected=true`, `oracle.sh:159-163`). M2 = features built (`fidelity_ok=true`, `oracle.sh:165-169`). M3 = both (`oracle_pass`). C1/C2/C3 mean the oracle's `constraints.{1,2,3}` booleans (`oracle.sh:151-155`). Tests are one-sided Fisher exact, G greater than C, recomputed from the raw `oracle.log` of every run, never from a row's self-reported flags.

Copied verbatim from the first-experiment section 2:

- KR1 (verdict SUCCESS) needs all of:
  (a) `M1_G - M1_C >= 6` runs (20 points) and Fisher p <= 0.05. With C at 5/30 that means G >= 12/30 (p=0.042); with C at 3/30, G >= 10/30 (p=0.029).
  (b) M2 not traded away: `M2_G >= M2_C - 3` runs (no more than 10 points lower).
  (c) `M3_G >= M3_C`.
  (d) Mechanism seen: at least 3 G runs where a violation was reported, a retry ran, and the next check passed.
  (e) Validity, see KR4.
- KR2 (verdict FAIL) when either:
  (f) no effect: Fisher p > 0.20 and `M1_G - M1_C < 3`; or
  (g) FAIL-TRADE: `M1_G - M1_C >= 6` but `M2_G < M2_C - 3`. Constraints bought with function is a fail, not a partial win.
- KR3 (verdict INCONCLUSIVE) is everything else, including a validity failure. The decision rule is closed: no optional stopping and no n extension after reading results. A follow-up needs a new plan. Power check (simulated, 4000 draws each): true rates 50% vs 15% detect at 86%; 40% vs 15% at 61%; 30% vs 15% at 27%. A modest real effect will often land in INCONCLUSIVE, and that is an accepted outcome.
- KR4 (validity): >=27 valid runs per arm and every row on the pinned CLI version. A valid run is one whose five turns all completed and whose `failure_class` is not `infra_fail`; `capability_fail` rows count. Infra failures are re-run, at most 3 times each. If infra failures exceed 10% of attempts in either arm the verdict is INCONCLUSIVE.

KR5 analogue (oracle frozen): `evals/orchestration/tasks/t14-constraint-horizon/{oracle.sh,CONSTRAINTS.md,turns/,task.md}` and `repo/` are byte-identical at the start and end of the batch (KR5 hashes). The batch records `git hash-object` of each in its header and the analyzer refuses to run on a mismatch. The oracle must not change, including for "obvious" bugs found during the run.

KR6 analogue (instrument): `--gate-retry-feedback violations` reproduces the first-experiment retry text byte for byte. Negative control in tests: features-only gaps do not trigger a retry in `violations` mode.

Reported, not gated: the snapshot comparison in section 3.5 (gaps persisted, fixed and introduced by a retry, grouped by trigger kind). It does not enter the verdict. Verifier-vs-oracle disagreements are reported as in the first experiment and do not change KR numbers.

### 2.1 Independent variable (frozen)

Trigger (new mode `violations+features`): after a turn, a retry fires when the verifier reports violations **or** reports `feature_gaps`. `feature_gaps` must be only the features requested up to and including that turn. Retry cap stays 2 per turn.

Message, fixed template. Violation lines are exactly the first-experiment sentence, one per violation:

"The change you just made breaks project rule N: `<rule>`. Observed: `<evidence>`. Fix this without removing any feature you were asked for, and keep every other rule."

When `feature_gaps` is non-empty, add one line per gap:

"A feature you were asked for so far is not working yet: `<gap>`."

and then one final line:

"Keep the parts that already work; do not delete or break any existing feature."

When there are no gaps, the message is byte-identical to the first experiment (violation lines only, no keep line).

Flag. The harness gets `--gate-retry-feedback violations|violations+features`. The harness default is `violations` (first-experiment behaviour reproduced byte for byte). The batch driver gets `--retry-feedback` with default `violations+features`, passes it only to the G arm (C stays observe and sends nothing), and records it in the results header. The default is written here in the plan.

### 2.2 Verifier check (finding, read before this plan was written)

Read of `evals/orchestration/tasks/t14-constraint-horizon/gate/verify-turn.js` (`verifyTurn`, the calls after `cli.py run`):

- The run timestamp gap (`run output has no timestamp field`, `enforceC2`) runs on every turn from turn 1. Turn 1 is when the timestamp column is requested (`turns/01.md`).
- The export check (`export did not write a file`, `callC1Export`) runs only when `turn >= 3`. Export is requested at turn 3 (`turns/03.md`).
- The bad-flag and bad-date exit-code checks (`run --bad-flag exited 0`, `run --since bad-date exited 0`, `callC3`) run only when `turn >= 4`. Error handling is requested at turn 4 (`turns/04.md`).
- The footer checks (`stdout has no Total rows footer`, `export has no Total rows footer`, `export file unavailable for footer check`, `callFooter`) run only at turn 5. The footer is requested at turn 5 (`turns/05.md`).

No gap check can fire before its feature is requested. S1 only adds a test pinning this property. S1 does not change the turn gates.

### 3.5 New observation (no behaviour change to the verdict)

Before every retry the harness copies the repo state (`TEMP_REPO`) to a snapshot directory under the run out dir. The directory name is `snapshot_<turn>_<k>`, where `k` is the retry index, taken before the retry prompt is sent.

The analyzer gets an additional output only (no change to verdict logic): per retried G run, run the verifier on each snapshot and compare with the next `gate.jsonl` record to count gaps persisted, fixed and introduced by a retry, grouped by trigger kind (violations only, features only, both). A retry that breaks a working feature shows up as an introduced gap. Reported, not gated. It answers first-experiment section D.

## 5. Test / validation

No new test files in the pre-registration commit. S1 adds tests. Required controls:

- `--gate-retry-feedback violations` (the harness default) produces retry text byte-identical to the first experiment when the only findings are violations.
- Negative control: features-only gaps do not trigger a retry in `violations` mode.
- `violations+features` with a non-empty `feature_gaps` list appends one line per gap in the fixed sentence, then the keep line, and with an empty `feature_gaps` list emits violation lines only.
- A retry writes `snapshot_<turn>_<k>` from `TEMP_REPO` before the retry prompt is sent.
- Turn-gating pin: the export gap is absent before turn 3, the bad-flag and bad-date gaps are absent before turn 4, the footer gaps are absent before turn 5, and the run timestamp gap is the turn-1 gap.

## 6. Risks

- Feature-gap retries add turns and can move M2 either way. That is the measured variable, not a reason to stop early.
- A snapshot that is taken after the retry prompt, or that the model can read, would spoil section D and KR6. The copy is outside the temp repo the model sees, and it is taken before the prompt is sent.
- Arm order, version pin, infra cap, and oracle freeze stay as in the first experiment. A version mismatch stops the driver (`reason=version`).
