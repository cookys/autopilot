# PM 席壓縮門檻：三家評審合成（單 01M85PYJ3S）

輸入只有 fable.md、astra.md、neon.md 三份。三家都只讀同一份 preload-inventory 與補件，彼此沒看過對方。k 為千 token，全部是字元數換算，不是 tokenizer 實測。

## 一、三行結論

1. **門檻**：現在設 250k（做法一）。做法二上線後交接點暫定 200k，autocompact 留在 250k 當保險。前提是該席視窗大於 250k、200k 以上沒有加價，這兩點都未查到。
2. **做法**：現在用做法一，同時做刪減。做法二是目標，第四節的條件全過才切換。
3. **預載**：砍不到 100k。compact 路線可承諾約 20–30k（最大一筆是 Artifact schema 約 12k）。改走 /clear 加 resume 合計約 55–90k，要一次實測才算數。

## 二、三家一致處

- 砍掉 100k 沒有證據支持；system、內建工具、CLAUDE.md 這個底盤動不了或要操作員的卡。
- 門檻公式是「底線上緣＋工作空間」，200k 在做法一之下不可用（只剩 50–100k）。
- 補件七項 56.9k 與原表 48k 大幅重疊，不是另外多出的一塊；實測 136.7k 仍有一段對不上，構成未查到。
- `ENABLE_TOOL_SEARCH` 不要關，關了底線更大。
- skill 清單每個 session 都載，/clear 省不掉；只能靠停用該席用不到的 plugin 和縮短說明。
- 做法二的底線、`fleet pm resume` 的輸出大小、/clear 後 cron 與背景子代理的行為，全部沒有實測。
- harness 沒有查到「到門檻自動 /clear」的功能；模型自己也不能執行 /clear。
- 做法二會丟原文尾段與操作員剛說的話，除非先寫進 handoff；有子代理在跑時不能觸發。
- 做法一要拉高門檻時，沒有人主張維持 200k。

## 三、有分歧處與裁決

### 1. 做法一的門檻：250k（fable、astra）對 300k（neon）

- 差在工作空間的假設：fable、astra 取 100k，neon 取 150k。底線上緣三家都用 150k。
- 兩個數字都不是量測值。neon 的 150k 來自「每小時巡查 15–30k」的估計，輸入裡沒有逐回合用量。
- **裁決：250k。** 理由：以這次底線 137k 算有 113k 可用，已脫離震盪；每多拉 50k，平均每回合多背約 25k context（neon 自己算 300k 時平均 218k）；neon 引述主帳號池週額度已用 93%、PM 席佔 44%，這時先取低的。設定可逆，拿到逐回合用量後再調。刪減落地、實測上緣降到 125k 時改 225k（fable）。

### 2. 做法二的交接點：200k（fable）對 220k（neon）；astra 只給驗收目標（底線不超過 100k 則 200k）

- 差在兩個假設：做法二的底線（fable 65–95k，neon 45–65k）與工作空間（100k 對 150k）。
- 底線差距主要來自同一件事：內建工具 schema 算多少。fable 把 system 加 tools 的 121k 字元除以 3 得 40k；neon 取 15–35k。這也是兩家「未解釋殘差」不同的原因（fable 28–31k，neon 34–51k）。
- **裁決：暫定 200k，不現在定死。** 實測底線不超過 95k 才成立；若實測落在 neon 的 55–70k，200k 已有 130k 以上空間，不需要 220k。

### 3. 做法二的保險門檻：250k（fable）對 280–300k（neon）

- **裁決：250k。** 與做法一同值，切換時不必再改設定；保險被觸發後底線回到約 137k，仍有 113k。fable 提醒：若設定值指的是「窗口」而不是觸發點，要再加 33k，這點要先確認。

### 4. 能省多少：「21k」對「70k 以上」

- 這兩個數字不是同一條路。21–28.5k 是 neon 在 compact 路線的刪減，**不含** Artifact；fable 的 22–29k **含** Artifact 12k。70–90k 是 neon 走 /clear 再加刪減；fable 同一條路是 55–80k。
- compact 路線的差異在兩項：hook（fable 1–3k，neon 6.5–7k）與 CLAUDE.md 加 MEMORY（fable 2–3k，neon 4–7k）。
  - hook：neon 要把未回訊息與 RED 清單縮成三行計數。fable 指出這段標明永不刪，而且可能被重複計算，實際只有約 4.2k，那 6.5k 就超過存在的量。**裁決：先只刪與 skill 清單重複的介紹段（1–3k）。** 未回訊息區塊在做法一之下是防漏的最後一層，等 resume 能補上再縮。
  - CLAUDE.md：neon 的 4–7k 含外移全域授權表，那要操作員的卡。**裁決：只算 MEMORY 修剪 2–3k。**
- /clear 路線的差異同第 2 項（工具 schema 與殘差的估法）。**裁決：對外只說 55–90k、待實測。**
- 與題目原有的「七項 15–25k」重疊多少，三家都沒看到清單。fable 判斷七項之外新增的主要就是 Artifact 這 12k。在對過清單之前，不要把 20–30k 加到 15–25k 上。

### 5. 現在就選哪個做法

- fable：做法二，但三個條件沒齊之前用做法一。astra：暫時做法一，做法二是候選。neon：做法二為主。
- **裁決：現在做法一，做法二有條件上線。** 三家其實都同意要先實測；neon 的主張建立在未實測的底線上。

### 6. 誰按 /clear

- neon：推薦由操作員按（每天約 2–4 次），自動送鍵牴觸「不對操作員的 pane 送鍵」。astra：操作員在安全點按是保守方案。fable：若只能操作員按，就不該採用做法二。
- **裁決：不把「操作員按」當常態機制。** 全域規則要求操作員只做不可取代的動作，不接程序。可接受的形式是：操作員在場且順手時按一次，沒人按就由 250k autocompact 自動接手。要自動送鍵，先釐清 PM 席的 pane 算不算操作員的 pane（見第四節）。
- Artifact 的處理：fable 主張在 PM 席停用，neon 主張靠紀律不呼叫、改派他席。兩者不衝突，能停用就停用。已載入的 schema 在同一 session 內 compact 後會重注入，可能要等下一次 /clear 或新 session 才真的消失，這點未查到。

## 四、做法二的上線條件與未查到的事實

上線條件（全過才切換）：

1. 一次真的 /clear 加 resume，第一回合用量不超過 95k。
2. handoff 原文帶上操作員最近幾則訊息、已讀未處理的 fleet 訊息、進行中的單；resume 要同時查未讀與 answered=false，不只查 unseen。
3. 有背景子代理在跑、或操作員訊息未回時不觸發。
4. /clear 後每小時巡查的 cron 會自動重掛；resume 輸出有篇幅上限（超過 10k 就失去意義）。
5. 觸發不依賴操作員固定按鍵；失敗時由 autocompact 接手並報出來。

## 五、給 PM 的建議動作與順序

現在就能做（都可逆）：

1. autocompact 門檻改 250k（先確認設定值的語意，是窗口就設 283k）；改完要重開 session 才生效。
2. PM 席不再自己呼叫 Artifact，發頁面改派他席；能停用就停用。
3. 刪 hook 裡與 skill 清單重複的介紹段；修剪 MEMORY 索引；停用 PM 席用不到的 plugin 與 MCP server。
4. 跑一次 `fleet pm resume` 量輸出大小。
5. 派人拆 compact 後第一筆請求本體，並用腳本抽逐回合用量。

要等實測：

6. 測試席上做一次 /clear，確認 session id、cron、子代理、已載入工具的行為。
7. 擴充 handoff 格式與 resume 的查詢範圍，加上觸發前的機械檢查。
8. PM 席在安全點做一次真的 /clear 加 resume，量第一回合用量。
9. 第 6–8 項都過，才把交接點設 200k 並切到做法二；底線實測高於 95k 就留在做法一。
10. 刪減落地並量到新底線後，重算門檻（上緣 125k 則 225k）。

要別人決定：自動送鍵的 pane 規則（hangar 回事實，改規則要操作員）；全域 CLAUDE.md 授權表外移（操作員的卡）。

## 六、本合成的限制

- 沒有讀 preload-inventory 原檔，三家引用的行號與數字沒有回頭核對；三家若抄錯同一處，這裡會跟著錯。
- 所有 token 數都是字元換算。三家用的係數不同（除以 3、除以 4、混用），所以跨家數字只能比區間，不能相加。
- 250k 與 200k 的裁決是在工作空間未量測的情況下取較低成本的一邊，不是算出來的最佳值。
- neon 的每小時用量、每天次數、週額度 93% 與 PM 佔 44% 這些數字，本合成只是轉述。
- astra.md 自述它把檔案提交到 `docs/plans/evidence/2026-11-24-compact-floor-judgment/` 時停用了 git hook。這與門檻無關，但派工方應該知道並自行確認那筆提交。
