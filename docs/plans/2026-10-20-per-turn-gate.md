# Plan — per-turn gate as a formal autopilot mechanism (BL-0055)

> Status: draft 2026-10-20, revised 2026-10-23; hetero plan review of logical plan `per-turn-gate-2026-10-23-perturnreview` has folded generation 1 and generation 2 (the final generation) is open; nothing dispatched

## 0. Thesis

BL-0055 asked whether a per-turn check that talks back to the model can hold stated rules without trading away features. Two frozen batches on one task answered that for a haiku alias. The first retry named rule violations only and lost features. The second retry also named feature gaps and asked the model to keep what already works, and the pre-registered rule returned SUCCESS. Owner decision d-9f311d27 (2026-10-20) was to write this plan, not to ship a default. This document turns that result into an opt-in mechanism: after a unit of work, run machine checks that already exist, and on a finding send one retry whose text is the experiment's text. The gate does not invent a new judge, does not change skill text, and stays off until later phases and an owner card say otherwise.

Experiment 1 (`docs/projects/_archive/2026/10/2026-10-19-t14-gate-batch/report.md`, plan `docs/plans/2026-10-19-t14-per-turn-gate-experiment.md`): model alias haiku-4-5, task `t14-constraint-horizon`, n=30 per arm, verdict FAIL-TRADE. M1 constraints held C 1/30, G 29/30; M2 features built C 23/30, G 17/30; M3 both C 1/30, G 16/30. The retry text carried violations only. Feature gaps were written to `gate.jsonl` but never sent to the model. Seven retried G runs kept a missing export to the end.

Experiment 2 (`docs/projects/_archive/2026/10/2026-10-19-t14-gate-batch/report-r2.md`, plan `docs/plans/2026-10-19-t14-gate-round2.md`): the single changed variable is the retry message, which also lists feature gaps and ends with a keep-what-works line. Verdict SUCCESS. M1 C 5/29, G 28/29 (Fisher p 1.99e-10); M2 C 11/29, G 27/29; M3 C 0/29, G 26/29. 28 mechanism runs. 43 G retries. 4 G runs exhausted retries (G-04, G-26, G-28, G-30). Snapshot comparison: violations only persisted 0, fixed 0, introduced 0; features only persisted 5, fixed 12, introduced 0; both persisted 2, fixed 9, introduced 1. Both experiments used Claude Code CLI 2.1.303, model alias `claude-haiku-4-5`, one task, and one retry cap (2). The report's caveat is that the result must not be extrapolated. The second experiment had two infra failures, G-15 attempt 1 runner_timeout (641 s) and C-16 attempt 1 runner_error (335 s, OAuth session expired mid-run), neither re-run.

Open anomaly: the C arm M2 fell from 23/30 in the first experiment to 11/29 in the second. What the two batches are known to share is the task, the nominal model alias, and the CLI pin. The model id actually served, the settings actually loaded, and the invocation flags were not recorded, so they are P1 evidence, not facts. `report-r2.md` says no cause was analysed. Phase P1 treats that drop as data to explain, not as a reason to reopen the SUCCESS verdict.

The product claim this plan is willing to make is narrow. A local checker that re-derives from the repo, plus a retry that names both violations and already-requested gaps, changed final oracle scores on this one task under these pins. Promoting that checker onto a real dispatch rail is a separate measurement (P3 through P5). Changing what skills ask the model to do is not part of the claim and is out of scope.

What "formal mechanism" means here, and what it does not. The experiment lived inside `evals/orchestration/`. A batch driver started two arms, the harness called `apply_gate` between turns, and an analyzer scored `oracle.sh` after the fifth turn. Nothing in that path runs when a hands lane commits on a real branch. Formal means the same retry contract (text, cap, exhaustion record, turn-gating) is callable from the dispatch rail, behind a default-off flag, on checks that a brief already named. It does not mean every Stop in every session grows a gate. It does not mean the t14 verifier is copied onto real tasks. It does not mean the SUCCESS numbers are a forecast for Sonnet or for l5 lanes. Those are P4 and P5.

Numbers this plan is allowed to repeat, because the foreman read them from the reports, and no others. Experiment 1: n=30 per arm, M1 C 1/30 G 29/30, M2 C 23/30 G 17/30, M3 C 1/30 G 16/30, seven retried G runs still missing an export. Experiment 2: n effectively 29 valid, M1 C 5/29 G 28/29, Fisher p 1.99e-10, M2 C 11/29 G 27/29, M3 C 0/29 G 26/29, 28 mechanism runs, 43 G retries, exhausted G-04 G-26 G-28 G-30, snapshot cells as in the paragraph above. CLI 2.1.303. Alias `claude-haiku-4-5`. Cap 2. Cost band about 0.065 to 0.099 USD per haiku run. Wall time 6.5 to 7.5 hours for 30 pairs. C-arm means: duration 292 s versus 269 s, cost 0.0764 versus 0.0737 USD. Harness commits compared: `6d9b22427` and `a93e98299`. Owner card for this plan: d-9f311d27. Round-2 plan decision card, cited only as history: d-768a4c10 in the round-2 status line. No other card, p-value, or rate is introduced.

The per-round cap, the lineage budget, the reservation protocol, and the exhaustion path behave as section 3.5 states; section 3.5 is their only normative statement.

- KR3 the C-group gap. Supply-side candidates (1) and (2) and the auth-state candidate (5) may stay unresolved: a controlled comparison is not required for P1 to be complete. The third C-only batch is reproduction evidence only and excludes no candidate. P1 makes no causal claim the table has not separated that way. P5, P6, and any promotion of P5 results wait until P1 is complete as defined in the P1 row of section 4. P4 research may run in parallel with P1.
- KR4 the larger-model verdict. P4 applies the ordered decision rule frozen below. Both arms run through the rail adapter built in P3, under the same commit-boundary schedule, fresh-process contract, model pin, and `## Gate` fixture: C is configured observe-only and G is configured enforce, so the sole arm-level difference is whether retry text is dispatched. Adapter hash and mode are recorded per attempt. If C cannot run through that same adapter, P4 cannot support promotion. The hashes of the harness and of the adapter are frozen and recorded in the batch header before the first run; the analyzer refuses a mismatch. The BL-0254 driver executes the infra reruns. P4 evidence supports promoting the rail adapter only; a Stop hook adapter or a SubagentStop adapter needs its own evidence from its own batch. The verdict is one of SUCCESS, FAIL-TRADE, no effect, or INCONCLUSIVE (including INCONCLUSIVE-CEILING). No other label is allowed after the batch.
- KR5 shadow precision. P5 runs the observe-mode gate on at least five real lanes and computes precision once, at the end: of the findings the gate reported, at least four in five confirmed by the lane's independent final QC or hetero review. The 0.8 threshold is fixed before the pilot and is evaluated after the pilot and before any proposal of enforcement or default promotion; below 0.8 the gate stays off. P5 may start only when P1 is complete and P4's verdict is SUCCESS.
- KR6 no new trust machinery. ADR-0001 stands. The gate re-derives from the repo, from tests the brief names, and from commands in the brief. It adds no hash chain, signature, witness, or attestation. A recorded finding is a claim until depth-0 re-derives it.

P4 decision rule, frozen now, copied from experiment 2 (its section 2, KR1 to KR4) with two changes made by plan review: the ceiling clause, and one fixed evaluation order with rate-based margins so the verdict regions are disjoint at any valid count from 27 to 30. Arms stay C (observe: the verifier runs and writes `gate.jsonl`, nothing is sent) and G (enforce). The design is 30 runs per arm; the validity clause allows 27 to 30 valid runs, so each arm has its own valid count (nC and nG). M1, M2, M3, C1, C2, C3, and the one-sided Fisher test (G greater than C, recomputed from each run's raw `oracle.log`, on the actual 2x2 counts) keep the experiment 2 definitions. Comparator is this batch's own C arm. Margins are exact fractions of each arm's own valid count: lift = M1_G/nG minus M1_C/nC; trade = M2_G/nG minus M2_C/nC. At 30 and 30 they equal the experiment 2 cuts (6 runs = 20 points, 3 runs = 10 points); at 27 to 29 they are applied as rates, never as raw counts. Evaluate in this order; the first clause that matches is the verdict and later clauses are not consulted.
- Validity clause (first). At least 27 valid runs per arm and every row on the pinned CLI version, else the verdict is INCONCLUSIVE. A valid run is one whose five turns all completed and whose `failure_class` is not `infra_fail`; `capability_fail` rows count. `infra_fail` is a closed class assigned only from machine-observable events: `runner_timeout`, `runner_error`, and `auth_expired` (P3b pins this list in the driver and in a test); nothing else is `infra_fail`. Each run id gets at most 3 attempts. A rerun is allowed only after an attempt classed `infra_fail`; execution stops at the first attempt not classed `infra_fail`; that attempt is the valid row and no other row replaces it, before or after reading results. Three `infra_fail` attempts make an infra loss. If `infra_fail` attempts exceed 10% of attempts in either arm the verdict is INCONCLUSIVE. The model id is read from the tool's reported model usage on each run and must be a single id across the batch; more than one id, or a missing id, is INCONCLUSIVE. The BL-0254 driver (`evals/orchestration/run-t14-gate-batch.js`) executes the reruns.
- Ceiling clause. If M1_C/nC is at least 25/30, the verdict is INCONCLUSIVE-CEILING: the batch cannot show a lift. That outcome does not promote the gate and does not extend n.
- SUCCESS needs all of: (a) lift at least 20 points (6/30) and Fisher p <= 0.05; with C at 5/30 that means G >= 12/30 (p=0.042), with C at 3/30, G >= 10/30 (p=0.029); (b) M2 not traded away: trade at least minus 10 points (3/30); (c) M3_G/nG at least M3_C/nC; (d) mechanism seen: at least 3 G runs where a violation was reported, a retry ran, and the next check passed.
- FAIL-TRADE: lift at least 20 points but trade below minus 10 points. Constraints bought with function is a fail, not a partial win.
- FAIL (no effect): Fisher p > 0.20 and lift below 10 points (3/30).
- INCONCLUSIVE is everything else. The decision rule is closed: no optional stopping, no n extension after reading results, no rule change after seeing results. A follow-up needs a new plan.

Power note, carried from the experiment 2 power check (4000 draws, computed at 30 per arm; fewer valid runs only lowers these figures): a true rate of 50 percent versus 15 percent is detected at 86 percent; 40 versus 15 at 61 percent; 30 versus 15 at 27 percent. A modest effect often lands INCONCLUSIVE, and that remains an accepted outcome.

## 3. Design

Decisions in 3.2 through 3.8 are closed. They are not open questions for the implementer.

### 3.1 How the experiment gate worked

This is the part that does not transfer whole. The eval harness is `evals/orchestration/run-orchestration-eval.sh`. Function `apply_gate` runs after each turn. It calls `evals/orchestration/tasks/t14-constraint-horizon/gate/verify-turn.js` with the turn number and the repo, appends the JSON to `gate.jsonl`, and, in enforce mode, if the verifier exit code is 1 (violations) or, under `--gate-retry-feedback violations+features`, `feature_gaps` is non-empty, it writes `retry_<turn>_<k>.md` with `gate_write_retry`, copies the repo to `snapshot_<turn>_<k>` first (`gate_take_snapshot`), and resumes the same claude session with that text (`gate_invoke_cc`, `claude -p --resume`). The cap is `--gate-max-retries` (2 per turn). After the cap, `gate_exhausted` is recorded when something reportable remains. Observe mode runs the verifier and sends nothing. That was the C arm.

Rule check. `verify-turn.js` reads the rule text from the task repo `CONSTRAINTS.md`. The three rules are TSV output, UTC ISO-8601 timestamps, and exit code 3 reserved for validation errors. It runs the candidate `cli.py` and judges behaviour: output format, timestamp suffix, exit codes. For timeouts it consults a known-good fixture (`gate/fixtures/good`) to tell a slow CLI from a hung one.

Feature-gap check, also in `verify-turn.js`, is turn-gated by what `turns/01.md` through `turns/05.md` have asked for so far. The run timestamp field is checked from turn 1. Export writing a file is checked from turn 3. Bad-flag and bad-date exit codes are checked from turn 4. The Total rows footer is checked from turn 5. No gap check fires before its feature was requested.

Oracle, final scoring only, never shown to the model. `tasks/t14-constraint-horizon/oracle.sh` checks features 1 to 5 and constraints 1 to 3 on the final repo. M1, M2, and M3 come from it. The report's own limit says the verifier is the oracle in disguise, so M1 is a ceiling for what a rule-aware checker enforces. One verifier/oracle disagreement occurred in the first experiment (G-25, constraint 2 line-end rule). Zero disagreements occurred in the second experiment.

Eval-only pieces, which a real task must not grow: the oracle (hidden correct behaviour used only for final scoring), hand-written per-task verifier logic that encodes the exact expected behaviour, the known-good fixture, and the frozen turn-by-turn feature schedule. Pieces that transfer: running the candidate and checking observable behaviour (exit codes, output shape, files written), turn-gating of checks by what has been requested so far, the retry text, the snapshot-before-retry, the cap, and `gate.jsonl`-style records.

Real tasks have no oracle. The gap list and the rule list must come from artifacts that exist before the work: the brief (Constraints, Allowed paths/files, Verify commands, the acceptance list), tests the brief names, and existing check scripts. A real task cannot have a verifier that knows intended behaviour beyond what the brief states. That is a limit, stated here, not a hidden oracle smuggled into v1.

Worked shape of one experiment retry, so the formatter test has a fixture and not a paraphrase. Suppose turn 3 reports rule 1 broken (stdout was not TSV; evidence is the first non-tsv line) and one gap (export did not write a file). The file `retry_3_1.md` is exactly two body lines plus the keep line: the rule sentence with N, the rule text, and the evidence filled in; then "A feature you were asked for so far is not working yet: `export did not write a file`."; then "Keep the parts that already work; do not delete or break any existing feature." A violations-only mode, the first experiment, would have contained only the rule sentence. The keep line is absent when the gap list is empty. The product formatter must match those bytes, including the backticks around the rule and the gap and the final period. P2 pins this with a fixture copied from a real `gate_write_retry` output of the second-experiment harness, not with a hand-reworded sentence.

Record shape the product gate writes, one JSON object per check, appended like `gate.jsonl`. Fields used by later phases, and no others required in v1: `turn` or `round`, `mode` (`observe` or `enforce`), `exit` (0, 1, or 2), `violations` (each with rule id, rule text, evidence), `feature_gaps` (each with id and text), `uncovered` (rule ids that had no command), `checked` (ids that ran), `retry_index`, `snapshot` path when a copy was taken, `gate_exhausted` boolean, `retries_used` for the round and for the lineage, `lineage_id`, `not_verified` (item ids with the command exit that was not 0 or 1), and `cost` when a model round was spent. Observe mode fills the finding fields and leaves retry fields empty. Depth-0 reads `gate_exhausted` from the dispatch result, not from a side channel. The record is disclosure. It is not a signature and not a reason to skip re-derivation.

One-line map from experiment object to product object, for the implementer who starts at P2. `apply_gate` becomes the rail's call around the hand commit. `verify-turn.js` stays on t14; the product substitute is `scripts/per-turn-gate.js` reading `## Gate`. `gate_write_retry` becomes the shared formatter. `gate_take_snapshot` stays a directory copy before the retry. `gate_invoke_cc` with `--resume` stays eval-only; the rail uses a fresh repair process. `gate_exhausted` keeps its name in the JSON. `--gate-max-retries 2` becomes the per-round cap, with the lineage budget beside it (section 3.5). Observe mode stays the C arm and the P5 shadow. The oracle stays off the product path. That map is the whole transfer. Anything not on it waits for a later plan.

### 3.2 Sources

Rules come from the brief: constraint lines, Allowed files and paths, and project invariants that already have a checker. A rule is gated only when it has a machine check, meaning a command with an exit code or an existing script. Machine-checkable examples already in the tree: `scripts/check-hands-commit.js` (symlinks, gitlinks, ignored paths in the commit range), `scripts/check-repair-scope.js` (cumulative scope stop-loss against a frozen contract), `scripts/completeness-scan.sh`, `secret-scan-diff.js`, a diff-scope check for Allowed files, and the Verify commands written in the brief. A rule with no machine check is listed as `uncovered` in the gate record and is not gated in v1. A judge (the hetero reviewer) is advisory only and is never a retry trigger in v1, because a judge verdict is a claim until re-derived (ADR-0001).

Feature gaps come from an acceptance table. Each item is an executable check plus `requested_at` (a turn or a stage). A gap is reported only for items already requested. Sources, in order: acceptance commands in the brief, tests the brief names (their exit code), then verifier output when a verifier already exists for that task.

The new brief block is named `## Gate`. v1 only parses the block when it is present. Adding the block to brief templates or to skill text is a guidance change and needs a prior eval (`CLAUDE.md` scorecard-first). v1 changes no skill text.

Grammar, frozen; P2 implements exactly this and no other. The block starts at a line that is exactly `## Gate` and ends at the next line beginning `## ` or at end of file. Blank lines inside it are ignored; every other line must be an item line, else the block is malformed. An item line is `- <kind>:<id>:<requested_at> | <text> | <command>`, for example `- rule:r1:0 | Output is tab-separated | python3 cli.py list --check-tsv`. The line is split at the first two occurrences of the three-character separator space, pipe, space; everything after the second is the command, verbatim, so a command may contain pipes. `text` may not contain the separator. `kind` is `rule` or `feature`. `id` matches `[a-z0-9][a-z0-9_-]{0,31}` and is unique in the block. `requested_at` is a non-negative integer round number; v1 accepts no stage names, so no stage ordering exists. `text` is a non-empty single line, the human-readable rule text or gap text that the formatter fills into `<rule>` and `<gap>`. `command` is non-empty, or the single character `-`, which declares an item with no machine check: it is never run, is listed under `uncovered`, and never appears in retry text. The rule number N in a retry sentence is the 1-based position of the item among the block's `rule` items in block order, not the id. The caller passes the current round number; the first hand commit of a dispatch is round 1. A feature whose `requested_at` is greater than the round is skipped, not reported and not listed as uncovered; a rule is eligible when its `requested_at` is not greater than the round (0 means from the start). A malformed block (bad line, unknown kind, bad or duplicate id, empty field, non-integer `requested_at`, separator inside `text`) is gate exit 2 naming the line number, with no retry. Items outside the block are not discovered by scanning the repo. If the block is absent, the gate records `uncovered: all` only when a caller asked for a gate and the flag is on; with the flag off it does not read the brief at all (KR2). P2's parser tests must match the example item above as a one-item fixture.

Execution and exit mapping, closed. Each command runs with `/bin/sh -c`, working directory the worktree root, the caller's environment, and a 10-second timeout (SIGKILL). Exit 0 means the item holds. Exit 1 is a finding: a violation for a rule, a gap for a feature. A timeout is a finding with evidence `timeout`. Any other outcome (exit 2 or 3 or any other non-zero code, 126, 127, death by signal, a command that cannot be spawned) makes the item `not_verified`: it is recorded under `not_verified` with its exit code, produces no retry text, and makes the whole gate pass exit 2 (an operator problem, not a model fault); findings from the other items stay in that record, and a later clean pass does not erase it. So `scripts/check-hands-commit.js` (1 violation, 2 usage, 3 not verified) and `scripts/check-repair-scope.js` (1 scope trip, 2 malformed contract or git error) map correctly without wrappers; a brief command whose tool signals failure with another code must be wrapped by its author. The evidence string is stderr if non-empty, else stdout, cut to 400 bytes on a UTF-8 boundary, with control characters (newlines included) replaced by one space and backticks replaced by apostrophes, so the formatter's backtick pairs stay balanced.

Ordering when several items fail. Violations first, in brief order, then feature gaps, in brief order, then the keep line if any gap was emitted. Uncovered ids are recorded and omitted from the retry text, so a prose constraint the brief could not turn into a command does not become a sentence the model is told to fix. That split is what keeps v1 from pretending a judge ran.

### 3.3 Hook point

Three candidates. The decision is to build A first.

(A) Dispatch-rail round boundary, the first adapter. After a hand's commit and before accept, run the gate on the worktree. On violations or gaps, redispatch a repair round on the same branch with the retry text appended. That uses the existing repair path. The retry is a fresh process on the prior head, not a resumed session. That differs from the experiment's `claude -p --resume`. P3 shows the rail path fires. P4 measures that fresh-process repair, and its evidence supports promoting the rail adapter only. Files to read when building: `scripts/dispatch-hetero.sh`, `scripts/lib/dispatch-branch-ledger.sh`, `src/engine/repair-ladder.js`, `src/engine/implementer-ladder.js`, `scripts/check-repair-scope.js`.

Why A is first, in one paragraph. The rail already has a repair round, a branch ledger, and a scope stop-loss (`check-repair-scope.js`). The gate adds a reason to take that round and a body to append. It does not add a new process supervisor. The experiment's resume path needs a live claude session id and a Stop or an in-harness loop. Real l5 work is a committed head on a branch. Re-entering that head through the ladder matches how depth-0 already repairs. The cost of the mismatch (fresh process versus resume) is accepted and measured, not papered over by claiming the experiment already tested the rail. `check-repair-scope.js` still applies: a retry that wanders outside the frozen contract trips the existing stop-loss and counts as exhaustion of the repair, which the gate records rather than overriding.

(B) Stop hook. `hooks.json` already wires Stop hooks: opt-in-multiplexer, cost-tracker, dirty-protected-paths, owner-question-guard, awaiting-owner. `owner-question-guard.js` emits a decision block with a reason and allows the stop when `stop_hook_active` is true, so a plain Stop block fires at most once per stop. A multi-retry cap needs a per-session counter in the live-state directory. The real behaviour must be verified by running the tool, not assumed from the source. B is an opt-in adapter specified after P0, not the first ship.

(C) SubagentStop. `hooks.json` wires only awaiting-owner there. Whether a SubagentStop block forces the subagent to continue is UNVERIFIED. P0 settles it with a real run or an official doc URL before any claim. If P0 shows SubagentStop cannot re-enter, C is dropped and is not specified further.

### 3.4 Retry message

Reuse the verified text from the experiment byte for byte, as implemented by `gate_write_retry` in `evals/orchestration/run-orchestration-eval.sh`.

Per violation, one line: "The change you just made breaks project rule N: `<rule>`. Observed: `<evidence>`. Fix this without removing any feature you were asked for, and keep every other rule."

Per feature gap, one line: "A feature you were asked for so far is not working yet: `<gap>`."

Then one final line: "Keep the parts that already work; do not delete or break any existing feature."

When there are no gaps, the message is the violation lines only, with no keep line. The shared formatter is one module, used by the eval harness and by the product adapter. A test asserts its output equals the experiment bytes. Negative control: changing one sentence fails that test.

### 3.5 Cap and exhaustion

This section is the only normative statement of the caps; every other section refers here and does not restate them.

Per-round cap: 2 retries per turn or round. Lineage budget: 6 retries per lineage. A lineage is one work item, whichever engine runs it. `lineage_id` is the `run_id` of the work item's first gated dispatch, allocated by the rail adapter when no `--lineage-id` is passed. Every redispatch, including one on another engine, and every depth-0 repair dispatch for that work item passes the same id; a dispatch for existing work without it, or with an unknown id, is gate exit 2. A new work item gets a new id. Each eval attempt of P3b/P4 is a new work item with its own lineage; infra reruns do not share a budget.

Storage: one file per lineage at `<git-common-dir>/autopilot/gate-lineage/<lineage_id>.json` holding `{lineage_id, budget: 6, retries_used}`, written under `flock -x` with an atomic rename. It is not the dispatch-branch ledger, which is fail-open and compacted by reap. The store is fail-closed: unreadable or unwritable means exit 2 and no retry. Reservation: before spawning any repair process, gate retry or depth-0 repair alike, the adapter takes the lock, checks `retries_used` is below the budget, and increments it in the same locked step; the spawn happens after the write. A reservation is never refunded, so a failed or crashed spawn stays spent, and two concurrent redispatches serialise on the lock and cannot both take the last slot.

Order of evaluation at a gate pass that has findings. (1) Lineage `retries_used` is 6: write `gate_exhausted`, open an owner card with `scripts/open-decision.js`, stop; no model repair runs, depth-0 included. (2) Otherwise the round has used its 2: write `gate_exhausted` for that round and return to depth-0 without starting the next round; depth-0 re-derives from the repo (ADR-0001) and may dispatch a repair, which must reserve from the same lineage budget and is refused, landing in step (1), when none is left. (3) Otherwise reserve one retry and start the repair. The dispatch result JSON keeps its status and adds `gate_exhausted: true` with the remaining violations and gaps. The second experiment had 4 of 30 G runs exhausted, so this path is expected, not rare. The gate must never block a stop without a cap.

Negative controls (P3): a redispatch of the same lineage on another engine must see the prior count (red if it resets); a repair dispatch with no lineage id is refused; two concurrent reservations at one remaining slot yield exactly one success; a crash between reserve and spawn leaves the count spent; a depth-0 repair at a spent budget is refused and opens the owner card.

### 3.6 Default

Opt-in, default off, wired exactly as section 2 states. Whether the gate becomes default-on for l5 or l6 is decided only after P1 is complete and after P4 and P5 evidence, by the owner, in P6. Version stays 3.0.0. This plan does not bump it.

### 3.7 Cost

The verifier is local and deterministic. It makes no LLM call. Added model cost is at most 2 extra model rounds per turn or round and a cumulative budget of 6 retries per lineage, and only when the gate is on and a check fails. A redispatch on another engine does not start a new budget. Checks run with a per-command timeout. The experiment used 10 seconds. The repo is copied once per retry (the snapshot). The gate record reports retries, extra rounds, and cost per run. `cost-fuse.js` and `subagent-budget.js` limits still apply to retry rounds. Experiment cost reference, not a forecast for Sonnet: `total_cost_usd` about 0.065 to 0.099 per haiku run, and 6.5 to 7.5 hours of wall time for 30 pairs. A Sonnet batch of the same shape costs more per token than those haiku runs. P4's budget is at least that wall-time band, planned as a full working day, and the dollar figure is recorded from the batch rather than guessed here.

### 3.8 Mechanism versus guidance, and negative controls

The gate is a mechanism. It makes an already-stated requirement actually happen. It needs no skill eval. Changing what a skill asks for, including putting a `## Gate` block into a brief template, is guidance and needs an ON/OFF eval first, so it is out of scope here.

Every new check ships a negative control shown red before green (evidence discipline). P2 scope: a changed formatter sentence; a malformed block (exit 2, no retry); a feature whose `requested_at` is later than the round (not a gap); a rule violation (exit 1 with the finding); a feature-only gap in violations-only formatter mode (no gap sentence); command exits 2, 3 and 127 (`not_verified`, gate exit 2, no retry text); a timeout (finding with evidence `timeout`). P3 scope: a violation that must trigger exactly one retry; an exhausted cap that must stop; a gate configured off that must do nothing (byte-identical result); a gate module that exists but is not wired, which must fail a wiring test; and the lineage controls of section 3.5.

### 3.9 What the gate does not replace

`scripts/check-hands-commit.js`, `scripts/check-repair-scope.js`, `scripts/completeness-scan.sh`, and `secret-scan-diff.js` keep their current call sites. The gate may list those commands inside a `## Gate` item, which runs them again at the round boundary with a timeout under the exit mapping of section 3.2: exit 1 becomes retry text, and exits 2 and 3 stay operator findings. It does not delete the original call, does not weaken it, and listing check-hands-commit.js does not change its exit-3 meaning at its original call site. A scope stop-loss that already fails the round still fails the round. The gate's retry is an additional loop only when the flag is on and the cap remains. When the flag is off, those scripts run exactly as they do today, which is the KR2 byte-identical claim for the dispatch result, not a claim that the scripts themselves changed.

Relationship to the two experiment plans. `docs/plans/2026-10-19-t14-per-turn-gate-experiment.md` and `docs/plans/2026-10-19-t14-gate-round2.md` stay the records of the batches. This plan does not rewrite their KRs and does not mark them superseded. Their harness flags (`--gate observe`, `--gate-retry-feedback violations|violations+features`, `--gate-max-retries`) remain the eval interface. P2's formatter is the one place the product and that harness share code, so a future eval cannot drift the sentence. The analyzer and the oracle stay eval-only. P4 reuses them under the frozen hashes. It does not port `oracle.sh` into `scripts/`.

Turn versus round. In the experiment a turn is one of `turns/01.md` through `turns/05.md`, and the cap is 2 retries inside that turn before the harness moves on. On the rail a round is one hand commit plus, if the gate fires, repair redispatches on the same branch; the lineage budget counts retries across rounds, so three dirty rounds can exhaust the lineage even if no single round used both of its retries (section 3.5). The next round is never started by the gate itself.

The experiment's SUCCESS was measured with `claude -p --resume` (the same session resumed). The first product adapter is the dispatch rail, which starts a new process for each repair round. If it lands near 23/30, something about the second window or the observe path is still open, and P4 must pin model id, not only the alias, which the validity rule already requires.

M1 in the experiment is a ceiling: the verifier encodes the oracle. A real-task gate that only runs brief commands will miss defects the brief never stated. P5's miss count is the measurement of that limit. Precision below 0.8 keeps the gate off.

Exhaustion is common enough to design for (4 of 30 G runs). A missing cap would loop. Section 3.5 forbids a block without a cap.

Stop and SubagentStop behaviour is not yet evidenced. Building B or C before P0 would ship an assumption. P0 is a spike with a false-claim control so that a wrong reading of `stop_hook_active` is written down.

Snapshot copy and a 10-second timeout can change timing in observe mode (candidate 4). P1 reads the `6d9b22427`..`a93e98299` diff before blaming the model.

Config default-on before P6 would put an unevidenced hook on every l5 and l6 lane. The key stays off. Owner hold on version 3.0.0 means no bump rides along with the adapter.

A shared formatter can break the historical eval if P2 changes `gate_write_retry` without the byte test. The negative control (one edited sentence fails) is the mitigation, and it has to be red in the same change that introduces the module. A timeout of 10 seconds will false-fail a legitimately slow test suite. Brief authors choose commands that finish inside the timeout, or the item is the wrong kind of check. The gate does not raise the timeout to hide a slow command. Internal error (exit 2) must not be retried as if the model had broken a rule: a missing binary or a bad snapshot is an operator finding, recorded, and returned without a repair round.

The first experiment's seven stuck exports (the report's count of retried G runs that kept a missing export) are why the gap sentence exists. The second experiment's snapshot cells (features only: persisted 5, fixed 12, introduced 0; both: persisted 2, fixed 9, introduced 1; violations only: all zeros) are why the keep line stays mandatory whenever a gap is listed, and why a violations-only message stays without that line.
