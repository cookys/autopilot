## 4. 關鍵發現：分佈是雙峰 (bimodal)，量測是「視窗盲」

主 session（n=94）的 peak 明顯分兩群：

| 群 | peak 範圍 | 樣本 | 推測 |
|----|-----------|------|------|
| 小視窗群 | ≤ 210k | 25 (27%) | 200k-window 模型 / 短 session，牆在 ~200k |
| 大視窗群 | > 210k | 69 (73%) | 1M-window Opus（peak 至 948k），牆在 ~1M |

`message.model` 逐訊息有記（`claude-opus-4-8` 佔多數，另有 `claude-fable-5` / `opus-4-7` / `haiku` / `MiniMax-M3`），但 **`[1m]` 視窗開關不在 logged model id 裡** → 無法只靠 model id 分辨 200k vs 1M。實務上這個 fleet 有 73% session 跑破 210k（200k 視窗不可能），所以此使用者的「有效視窗」= 1M。

**一個絕對值 T3 無法同時服務兩群**：200k 對小視窗群是牆邊（合理），對大視窗群卻是第 4~14% 處（過早）。

## 5. 越牆時機 (T1/T2 是否過早)

| 門檻 | 首次越過位置（session 進度中位數） | 越過率 |
|------|-----------------------------------|--------|
| T1 = 100k | **4%** | 82/94 (87%) |
| T2 = 150k | **14%** | 76/94 (81%) |

T1 在 session 才走 4% 時就觸發、T2 在 14% 觸發，而這些 session 中位數還要再跑 ~470 則訊息。這不是「快結束的噪音」（noise ≤20 則僅 3~5%），而是 **過早狼來了**——在 1M-window fleet 上 100k=10% 預算、150k=15% 預算，提醒早到會被訓練成無視。

## 7. 建議

### T3（硬擋）建議：**視窗的 ~80%**，此 fleet 絕對值 ≈ **800k**

理由（最大化「真該切覆蓋」× 最小化「快結束了還被擋」，且硬擋須 fail-safe 偏向不擋合法工作）：

1. **硬擋是最具破壞性的 tier，只該在「近牆/病態」時觸發，不是「昂貴但合法」時。** 昂貴但合法 → 該由 T2 強力建議處理，不是 T3 擋。
2. 200k–500k 硬擋會擋掉 47~73% session，且它們中位還有 224~429 則合法訊息 → 對 73% 的 1M 視窗族群是災難。
3. 800k：只有 11% session 會到（真正失控的尾巴，max 948k、p95 867k、p99 948k），到這裡離 1M 牆只剩 ~200k 緩衝，硬擋合理。
4. **最關鍵：T3 應以「視窗百分比」表示（~80%），非絕對值。** 80%×200k=160k、80%×1M=800k，一條規則同時在各族群自己的牆邊觸發——絕對值做不到。若硬要單一絕對值，取此 fleet 的 800k。

### T1 / T2 在此分佈上「不合理」——為 200k 世界校準，但 fleet 有 73% 跑 1M

- 現況 T1=100k / T2=150k 假設 ~200k 視窗（50% / 75%）。實測在 1M fleet 上 T1 於 session 4%、T2 於 14% 就觸發 → 過早狼來了。
- **建議把三層都改成「視窗百分比」**：T1=50%、T2=75%、T3=~80–85%。
  - 200k 視窗 → 100k / 150k / ~170k（與現況幾乎一致，小視窗群不受影響）。
  - 1M 視窗 → 500k / 750k / ~800–850k（大視窗群才有意義）。
- 落地細節：`[1m]` 不在 logged model id，hook 無法只靠 model id 判視窗。可行做法：(a) 由使用者 config 宣告有效視窗（此 fleet=1M）；或 (b) 動態偵測——一旦本 session 任何 context_i 曾 >210k 即視為 1M 視窗，切換到 1M 級門檻。(b) 自我校準、無需外部設定，建議採用。

### 一句話

**T3 = 有效視窗的 ~80%（此 fleet ≈ 800k）；並把 T1/T2 也改成視窗百分比（50%/75%），否則現行 100k/150k 在這個 73%-跑-1M 的 fleet 上會在 session 前 4~14% 就狼來了。**
