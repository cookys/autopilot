五個結論詞，由左到右優先

1 · 最高要你決定

Claude Code 在等你核准權限或回答問題（attention 檔），或者有一個待決定檔還沒關。

2疑似卡住

某個派工超過 stall 門檻沒有新事件，watcher 在 envelope 上標了 stall。

3完成待驗收

campaign 的凍結進度 done = total，或這個 session 的任務全部完成。

4進行中

有活著的派工或未完成的任務。

5 · 最低待命

什麼都沒在跑。附上「停在等你指示 N 分」。

awaiting_disposition 是工頭在等 depth-0 處置，永遠不算「要你決定」。每一格的來源如果還沒接上，band 寫「來源未接」，不會寫成 0 或空白。

架構

四層：寫入端 → 檔案 → watcher → 讀取端

band 本身不算任何東西。它只讀檔案。所以 P1W 的核心工作是「每一格都要有會動的寫入端」：hook 在 session 裡自動寫、depth-0 照 skill 呼叫 CLI 寫、engine 在裁決時寫。每個專案只有一個 watcher，它定時把這些檔案組成一份快照，交給 band 和 review 頁。

agent 互動流程

一個 session 從開始到驗收，各角色誰寫了什麼

下面是一次 L-size 工作（例如 /l5）的時間線。左邊是你和 depth-0（你正在對話的這條主 thread），中間是 hook 和派出去的工頭與 hands，右邊是 watcher 和 band。每一條箭頭上寫的是「寫了哪個檔」。一般 dev-flow session 走同一條線，只是沒有工頭那一段。

身分與 scope

band 怎麼知道「這個專案、這件工作」是哪個

所有檔名的前兩段都是同一套身分：專案用 project_key（由 git-common-dir 算出，同一個 repo 的所有 worktree 都一樣），工作用 root_run_id。兩者合起來叫 scope，watcher 依 scope 分檔。session 的 marker 記著這兩個值，mod 讀 marker 就知道該看哪一份。

marker 的兩種角色（MARKER 列）

marker 原本只是「/l3–/l6 模式旗標」。現在它正式是每個 session 的身分紀錄：level: null 代表一般 session。派工 gate 只看有等級的 marker；一般 session 的 marker 只提供專案、root、phase 和開始時間。

SessionStart 只在這個 session 沒有 marker 時建立，絕不覆寫；所以 compact 或 resume 不會洗掉正在跑的 /l5。

live 目錄只認明確指定（LIVEDIR 列）

2026-10-05 一個探測把 AUTOPILOT_LIVE_DIR 指到 ext4 的 /tmp，程式拒絕後默默改用真實的 live 目錄，watcher 把測試資料寫進了真的 band 來源（已清掉）。

修法：明確指定的路徑一律照用，不在 tmpfs 只印警告；symlink 等安全性問題直接報錯，絕不改寫到別的目錄。

為什麼有些格要等 eval

機制列 vs 指引列

機制列：程式碼自己會發生

hook、watcher、engine、CLI 本身的行為。只要測試證明它會動就可以出貨，不需要 eval。例：awaiting-owner 在權限提示時寫 attention 檔。

指引列：要模型照 skill 文字去做

寫入動作只有模型知道該在什麼時候做（例如「這個問題超出 DOA」）。改 skill 文字前，要先用 ON/OFF eval 證明新文字真的讓模型做到、又沒有副作用（CLAUDE.md「成績單前置」）。
