## 0. Context / thesis

role-kit 只管派出去的 claude-native 子行程；PM、lead、lane 這些常駐席每次工作都吃同一份注入，沒有被任何機制依角色處理。PM 席的實測基準（PM 提供，每次事件的輸出量）：SessionStart 7758、UserPromptSubmit 907、PreToolUse 353。固定前綴裡最大的一塊是 32 個 skill 的描述清單：以 frontmatter `description` 的值摺行 trim 後算 UTF-8 位元組（不含 YAML 的 `>` 指示符），總和 8,818 B（codex 與 agy 的實量一致；fable 量到 9,090 B 是另一種量法）。

主張：先把 skill 描述縮短，並在動手之前先建好「不漏規則」的機械檢查；其次處理 SessionStart 的 `fleet pm resume` 和每次事件的 hook 輸出；最後在 PM 席實測前後差。

## 1. Problem

使用者目標：常駐席每次工作的注入量有可量到的下降，而且沒有任何一條規則因此在該出現的席位消失。現況的洞：

- 沒有一份「哪條規則靠什麼保證」的清單，瘦身後無法證明沒漏（`scripts/lib/role-kit.js:98` 只檢查一行 `A9:`）。
- skill 描述同時是路由條件，縮短可能讓該叫的 skill 沒被叫到（`references/skill-contract-card.md:16,54`）。現有 `evals/run-trigger-test.sh` 用 grep 掃整份 stream，會被 `system/init` 的 skill 清單誤導（正例恆過、反例恆敗，`evals/run-trigger-test.sh:55,78`），不能直接當基準。
- 內建 skill 無法由 `--plugin-dir` 拿掉（`project/plans/2026-11-05-rolekit-direction.md:69`），所以本計畫不做「過濾 skill 清單」，那部分不列。
- 實量 32 支描述：24 支超過 200 B（206–861 B），光 `Use when`＋`Not for` 兩段就超過 200 B 的有 think-tank-dialectic（512 B）、dev-flow（430 B）、think-tank（383 B）、ceo-agent（296 B）、research-to-ship（247 B）。所以「全部 ≤ 200 B」在保留觸發條件的前提下做不到，門檻要依實量訂。

## 2. OKR / KRs

- KR1：32 個 skill 描述的總位元組由 8,818 B 降到 6,800 B 以下（-23%），單支不超過 320 B。可達性依據：8 支原本 ≤ 200 B 合計約 1,390 B；若其餘 24 支平均 ≤ 226 B 即可達標。若 P0 量出的「Use when＋Not for 兩段下限」總和已超過 6,800 B，P0 必須在證據中改報可達的門檻，並回報 PM，不得悄悄放寬。
- KR2：trigger 命中率不低於 P2 量到的基準（同一組提示，縮短前後各跑一次，逐 skill 比較，沒有任何 skill 退步）。
- KR3：規則登記表涵蓋範圍內的規則，反向探針全部變紅，現況全部綠。
- KR4：在 PM 席用同一方法量，SessionStart／UserPromptSubmit／PreToolUse 每次事件的輸出量低於基準，並附前後數字。

## 2.5 Global Constraints (copied verbatim into every dispatch)

- 不新增任何 `.github/workflows`；所有檢查都是本機腳本。
- 不修改 `evals/rolekit/` 底下被凍結的檔（會讓 stamp 摘要失效），也不改 `evals/run-trigger-test.sh` 與既有的 `evals/trigger-prompts/*.txt`；新增的量具與題庫另建新檔。
- skill 的 `description:` 保留「Use when／Not for」結構和中英文觸發詞（`references/skill-contract-card.md:16,54`）；只能刪重複與贅詞，不能刪觸發條件。
- 紅線與授權類規則不得只留指標；必須在實際注入的內容裡出現，或由工具白名單或 hook 保證，並登記在規則登記表。
- 測試與量測不碰正式環境：不讀寫真的 `~/.claude`、credential、live store；真模型實跑用暫存 HOME 與 `CLAUDE_CONFIG_DIR`（沿用 `scripts/lib/eval-account.sh`），帶花費的實跑要有累計停損。
- 每個 commit 都過倉庫既有的 pre-commit 閘門（`.githooks/pre-commit:80-89` 的 `bash scripts/sync-all.sh --check --changed`）；動到 `skills/`、`scripts/`、`hooks/lib/`、`profiles/` 的 phase，必須同批同步 Codex 鏡像（`bash scripts/sync-codex-plugin-skills.sh`）、`profiles/*.json` 的重釘與 `scripts/CLAUDE.md`、`docs/scripts-inventory.md`。
- live 只跑 pin 住的 sha；換版要 PM 的 go。
- 證據裡不放主機名、帳號名、家目錄路徑。

## 2.6 Change-policy decisions

- **Compatibility impact**: `internal-only`。skill 描述屬內部路由文字，沒有外部消費者；`authorized-breaking` 不適用。
- **Dependency decision**: `none`。只用 Node 標準庫與既有腳本。

**P0 量具與基準**（歸 autopilot lane，不需要 live）
- 子指令與旗標（本計畫唯一的契約，後續 phase 照此用）：
  - `--check-baseline`：現況量值必須與 `baseline.json` 嚴格相等（描述總和與每支都要），差 1 B 即非零。這是 P0 防量法漂移用的，之後只在沒動描述的 phase 用。
  - `--check-budget --max-desc-total <T> --max-desc-each <E>`：只驗上限，P3 用。另外：描述總和不得高於上一個 commit 的量值（用 `git show HEAD:...` 重算）。
  - `--check-targets`：讀 `baseline.json` 的 `targets` 欄，被選中的兩個發送者輸出量需 ≤ 該欄的 50% 門檻值，P5 用。
  - `--compare <a.json> <b.json>`：兩份結果逐項比較，任何一項高於基準即非零，P6 用。
  - `--from-trace <jsonl>`：把 `pm-events.jsonl` 的 bytes 按 `event`、`hook` 彙總。
- 量法固定為：解析每支 `skills/*/SKILL.md` 的 frontmatter `description`，取值（不含 `>`、`|` 之類 YAML 指示符）、摺行、trim，算 UTF-8 bytes。基準總和為 8,818。
- 選兩個發送者的演算法（寫死，避免主觀）：對 `pm-events.jsonl` 中事件為 UserPromptSubmit 或 PreToolUse 的列，按 `hook` 加總 bytes，取總和最大的兩個 hook；兩者的基準值和 50% 門檻寫進 `baseline.json` 的 `targets`。若 trace 中這兩個事件的總 bytes 為 0，P5 取消並回報 PM。
- PM 事件 trace 由 PM 提供（匿名、不含訊息內容）；P0 開工前先向 PM 要這個檔，沒有檔不開工。
- 先量「描述的可達下限」：每支只留 `Use when` 與 `Not for` 兩段的位元組總和，寫進 `baseline.json`，供 KR1 可達性判斷。
- 驗收：指令見表；`--check-baseline` 對現況 exit 0。
- 反向探針：把任一支 SKILL.md 的 description 加 100 字元，`--check-baseline` 必須非零（回復後再綠）。
- 回滾：`git revert` 這個 commit（新檔與同步檔一起退）；沒有 live 影響。

**P1 規則登記表**（歸 autopilot lane）
- 範圍（v1）：autopilot 根目錄 `CLAUDE.md`、`AGENTS.md` 裡的規則樣式行（Never、must、禁止、一律），加 skill description 裡的 `Not for` 邊界（現有含 `Not for` 的 28 支；`fleet-usage`、`harness-maintenance`、`lead-watch`、`team` 四支沒有，列為警告，不阻擋）。外部來源（全域 CLAUDE.md、PM 的 CLAUDE.md）以 `external` 列登記，讀得到才比對，讀不到印「未檢查」，不算通過也不算失敗；這是 v1 的已知限制，寫在表頭。
- 每列保證方式三選一：`text`（注入內容必須含錨點）、`tool`（工具白名單拿不到）、`hook`（有預設開的 hook 攔截）。`hook` 類不只查接線：檢查腳本要用該 hook 的 deny fixture 實跑一次，輸出必須是 deny／block（`permissionDecision: "deny"` 或該 hook 文件記載的阻擋格式），把它改成只出 advisory 就變紅。
- 設定檢查：`check-seat-rules.js --config <settings-snapshot.json>` 讀一份席位 hooks 設定快照，若登記為 `hook` 保證的 hook 在該快照裡被關掉，輸出「保證失效：<rule id>」並非零；沒給 `--config` 時只檢查 repo 的 `hooks/hooks.json`。
- 驗收：指令見表。
- 反向探針（都寫進 test.js，缺一變紅就算沒做完）：刪掉登記表一列的錨點來源行；把某席位的注入內容拿掉一條 `text` 規則；把一個 `hook` 保證指到未接線的 hook；把一個 deny 類 hook 的輸出改成 advisory；`--config` 快照關掉一個 hook；來源檔新增一條規則樣式行但沒登記（`--strict` 變紅）。
- 回滾：`git revert` 這個 commit，連同同步檔；沒有 live 影響。

**P2 觸發基準**（歸 autopilot lane；有花費）
- 做：新增 `scripts/eval-skill-triggers.js`：用暫存 HOME 與 `CLAUDE_CONFIG_DIR`，對題庫逐題跑 claude，只計 stream-json 裡 assistant 的 `Skill` tool_use 的 `input.skill`，忽略 `system/init`；`--out` 存逐 skill 命中率，`--compare` 讀基準檔，只要任何一個 skill 的正例命中率或反例誤觸率比基準差就非零；`--budget-usd` 是累計停損，超過就停並以已量部分輸出、非零。
- 題庫：新增 `s10-should-trigger.txt`、`s10-should-not-trigger.txt`，涵蓋 P3 會動到的每一支 skill（目前實量 24 支超過 320 B 或在縮短範圍內的，完整名單由 P0 的 `baseline.json` 列出），每支至少 2 正 1 反，中英文各半；既有兩檔不改。
- 花費：先量 5 題的單題成本，乘以全題數得到預估，預估超過 6 USD 就縮題數並回報 PM，不加預算；實跑用 `--budget-usd 6`。
- 驗收：指令見表；`trigger-before.json` 存在，逐 skill 都有數字。
- 反向探針：寫一個只有 `system/init`、沒有任何 `Skill` tool_use 的 stream fixture，該題必須判「未觸發」；把一支 skill 的 description 換成無關文字，該 skill 的正例命中率必須下降。
- 回滾：只新增檔案（腳本與兩個新題庫）；`git revert` 即回到原狀，既有題庫從未被改。

**P3 skill 描述縮短**（歸 autopilot lane）
- 分批：按描述長度由大到小，每批 8 支，每批一個 commit。每批同步 `platforms/codex/plugin/` 鏡像和 `profiles/*.json` 的重釘（`SOURCE_HASH_DRIFT` 要清掉）。
- 目標：總和 ≤ 6,800 B、單支 ≤ 320 B（KR1）。
- 每批的驗收：`measure-seat-injection --check-budget`（總和不高於上一批）、`check-seat-rules.js` 綠、`eval-skill-triggers.js --compare` 無退步、`sync-all.sh --check --changed` 綠。全部批完後跑完整的表中指令。
- 反向探針：每批故意刪掉一支 skill 的 `Not for` 段，`check-seat-rules.js` 必須變紅，確認後復原。
- 回滾：每批 `git revert <commit>`（含鏡像與 profiles 的同批變更），只動 frontmatter，不影響 skill 本文；revert 後重跑 P0 檢查回到基準。
- 若某批命中率退步：該批不合併，只刪贅詞再試一次；同一批失敗兩次，把那幾支列入豁免清單 `project/evidence/s10/desc-waivers.json`（最多 4 支，每支記原因與保留的位元組數），`--check-budget` 對豁免的 skill 改驗「不高於原值」，並把豁免數計入 KR1 的結果回報。

**P4 pm-resume 封頂**（歸 autopilot lane；hook 行為，需要 PM 席實測）
- 現況：compact 路徑用 `digestResume(out, { maxChars: 3000 })`（`hooks/lib/pm-resume.js:112`），`digestResume` 對整個輸出 `.slice(0, maxChars)`（`:83-85`），且只保留 ULID，不保留列內容。
- 做：非 compact 的 startup／resume／clear 載入，改為「分段上限」：IN_FLIGHT 與 NEEDS_REPLY 的列整列保留、不計入軟上限（單列最長 400 字元，超過的列只縮短該列的描述，不丟列）；其他區段合計不超過軟上限 3,000 字元，被截的區段印「已省略 N 列」。compact 路徑維持原行為。
- 驗收：`node hooks/tests/pm-resume-cap.test.js`（新）加 `check-seat-rules.js`。
- 反向探針：fixture 有 20 列 IN_FLIGHT（單列 300 字元，合計超過軟上限）加 5 列 NEEDS_REPLY 加超過上限的其他區段，輸出必須含全部 25 列且其他區段被截；把保留邏輯換回整體 `.slice`，這個測試必須變紅。
- 回滾：`git revert`；hook 屬 pin 版本，沒換版前 live 不受影響。

**P5 每事件 hook 輸出**（歸 autopilot lane）
- 做：P0 的 `targets` 指名兩個發送者；只對「重複的提醒」去重或改走 advisory sink，deny／block 類輸出不動。
- 目標值固定為：兩個發送者的輸出量各自降到 P0 基準值的 50% 以下，`--check-targets` 讀 `baseline.json` 的 `targets` 欄。
- 驗收：指令見表。
- 反向探針：把其中一個 deny 類 hook 的輸出誤改成 advisory，`check-seat-rules.js`（P1 的 deny fixture 實跑）必須變紅。
- 回滾：`git revert`。

**P6 PM 席前後量測**（歸 PM／hangar 做上線，autopilot lane 驗證）

- 驗收：`--compare` 輸出三個事件與 skill 描述總和都低於基準，並附一行證據（數字）；`--config` 驗證綠。
- 反向探針：在快照裡關掉一個登記為 `hook` 保證的 hook，`--config` 必須印「保證失效」並非零。
- 回滾：換回上一個 pinned sha（per-host 備份與 sha16 由 hangar 依 rollout 流程記錄）。

## 5. Test / validation

- 腳本可驗的：P0、P1、P4、P5 的全部驗收，以及 P3 的位元組門檻。
- 需要真模型（有花費）：P2 與 P3 的觸發命中率，用暫存 HOME，累計停損 6 USD。
- 需要人看一眼：P6 的 live 前後數字（`needs_look: yes`）。
- 這份計畫的檢查都不證明模型一定遵守規則；只證明「文字有送到」或「工具拿不到」。

## 6. Risks + inversion

「什麼會保證失敗」：
