1. For `AWAITING_DISPOSITION`

The retained reference alone is insufficient because disposition resume is not necessarily read-only. The owner may classify a finding as must-fix, immediately returning the campaign to repair. The engine then relies on both identities:

- `commit`: the current candidate from which the next repair continues.
- `scope_implementation_sha`: the first candidate, which remains the campaign-wide churn and new-file baseline.

It also reuses the recorded branch and worktree lineage. That makes Git reconciliation part of validating executable authority, even though the already-completed review and verification are not rerun.

Option (a) fails closed if the candidate branch, tree, ancestry, or retained resource identity drifted. Its availability cost is that an otherwise read-only disposition could be rejected when the immutable commit still exists but its retained branch/worktree was removed outside the recognized cleanup protocol.

One residual failure remains in the current verifier: it accepts an absent worktree when cleanup is `pending_intent` or `completed` at [campaign-intake.js:605](</home/cookys/projects/autopilot/src/engine/campaign-intake.js:605>). If the owner then authorizes a repair, intake succeeds but retained-worktree reuse can fail later. That is a separate phase-sensitive resource-precondition gap, not a reason to omit Git verification.

Option (b) permits an integrity failure. For example, a Git replacement can make the recorded commit resolve to a different tree while preserving the textual commit ID. The persisted verification and focused review still describe the original tree, but a shape-only resume accepts them. Branch/worktree movement similarly advances durable disposition state before the repair dispatcher eventually discovers that the retained lineage no longer matches. In the worst case, stale verification evidence is reused for different effective content.
